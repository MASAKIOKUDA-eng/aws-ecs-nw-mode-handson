# 検証結果レポート：Amazon ECS ネットワークモード比較

> [handson-guide.md](handson-guide.md) の手順で実際に環境を構築・計測した結果です。形式は [result-template.md](result-template.md) に合わせています。
> 計測値は 1 日・1 環境での結果です。とくに k6 のレイテンシは各条件 1 回（1 分）しか取っていないため、傾向を見る材料として扱ってください。

## サマリー

| 観点 | 結果（ひとことで） |
|------|--------------------|
| スピード（起動） | **bridge / host が最速（中央値 2〜3 秒）**。EC2 の awsvpc は ENI の準備で 10〜12 秒、Fargate は 17 秒 |
| スピード（通信） | 1 接続のスループットはどのモードも約 5 Gbps で差なし。HTTP レイテンシも ALB 経由で p99 4〜10 ms、直接で 0.5〜0.8 ms と **実用上の差はなし** |
| コスト | 小さいタスク（0.25 vCPU / 512 MiB）では **B1（ENI 上限で 2 タスク/台）と D（ポートで 1 タスク/台）が 3〜7 倍割高**。B2（トランキング）と C は同等で、メモリが上限 |
| モニタリング | DevOps Agent は 6 件中 5 件で根本原因まで特定。awsvpc はタスク単位まで追え、bridge / host は Flow Logs と Container Insights の情報が粗くなる |
| セキュリティ | **host だけがコンテナから IMDS・ECS エージェント API・ホストの sshd に届く** |
| 結論 | 迷ったら **awsvpc（EC2 ならトランキング有効）**。bridge は「起動の速さ・密度」と引き換えに観測性と移行性を失う。host は特別な理由がある場合のみ |

### ガイドから変えた点

| 変更 | 理由 |
|------|------|
| リージョンを us-east-1 にした | 使用した AWS アカウントの既定リージョン |
| イメージのビルドを CodeBuild で実施 | 作業マシンのディスクに Docker を入れる空きがなかったため。一時的なスタックで作り、検証後に削除 |

## ① スピード

### 起動時間（秒、中央値 / p95）

`describe-tasks` の時刻から算出。各パターン 1 回目（空打ち）を除いた値です。

| パターン | network_ready | pull_started（ENI 待ちの目安） | pull_duration | startup_total | 備考（失敗の理由など） |
|----------|---------------|-------------------------------|---------------|---------------|------------------------|
| A | 6.1 / 16.9 | 14.9 / 25.4 | 1.6 / 2.0 | **17.0 / 27.2** | Fargate は毎回イメージを取得（約 1.6 秒） |
| B1 | ― | 11.9 / 19.4 | 0.1 / 0.1 | **11.3 / 18.6** | 10 個要求して **2 個しか起動できない**（`RESOURCE:ENI`）。n=8 |
| B2 | ― | 10.7 / 13.7 | 0.1 / 0.2 | **10.3 / 13.5** | 10 個すべて起動。B1 より p95 が安定 |
| C | ― | 2.1 / 3.2 | 0.1 / 0.1 | **3.0 / 3.8** | 10 個すべて起動 |
| D | ― | 2.1 / 2.6 | 0.1 / 0.1 | **1.8 / 2.3** | サービスを 0 にして 2 個で計測。サービスが動いたままだと `RESOURCE:PORTS` で起動不可。1 回目は直前のタスクのポート解放待ちで約 50 秒 |

読み方：

- EC2 のタスクは `connectivityAt` が `createdAt` と同じ時刻になるため、`network_ready` は常に 0 でした（ガイドの想定と違い、EC2 では ENI の準備時間を表さない）。代わりに **`pull_started`（作成からイメージ取得開始まで）が ENI の準備を含む待ち時間** になっています
- awsvpc（B1 / B2）と bridge / host（C / D）の差 **約 9 秒が ENI の準備にかかる時間** です。トランキング（B2）でも短くはならず、ばらつき（p95）が小さくなる程度でした
- Fargate は ENI の準備に加えてイメージ取得があり最も遅く、回によって 15〜27 秒とばらつきます

### スループット（Gbps、中央値）

iperf3、各条件 20 秒 × 5 回。負荷生成は AZ-b、計測対象は AZ-a。

| パターン | P=1 同一 AZ | P=1 AZ 間 | P=8 同一 AZ | P=8 AZ 間 | 再送（P=8 中央値） |
|----------|-------------|-----------|-------------|-----------|--------------------|
| A | 未計測 | 4.39 | 未計測 | **2.34** | 12,223 |
| B1 | 未計測 | 4.96 | 未計測 | 4.26 | 1,958 |
| B2 | 未計測 | 4.96 | 未計測 | 4.17 | 1,255 |
| C | 未計測 | 4.78 | 未計測 | **2.36** | 5,313 |
| D | 未計測 | 4.97 | 未計測 | 4.53 | 1,257 |

読み方：

- **P=1 はどのモードも約 5 Gbps**。これは AWS の 1 フローあたりの上限（プレイスメントグループ外で 5 Gbps）で、モードの差ではありません
- P=8 で A（Fargate）と C（bridge）だけ約 2.3 Gbps に下がり、再送も多くなりました。A は 0.25 vCPU のハード上限、C は docker0 ブリッジと NAT の処理が考えられますが、**CPU 使用率を同時に記録していないため原因は未確定** です
- c6i.large のベースライン帯域は 0.781 Gbps（バースト最大 12.5 Gbps）。20 秒程度の計測はバーストの範囲内で、長時間の転送ではベースラインまで落ちる点に注意が必要です

k6 の固定レート（`/1k`）。各レート 1 回・1 分。エラーと `dropped_iterations` はすべて 0。

| B2 | 3.8 | 5.8 | 4.9 | 6.7 | 2000 rps まで悪化なし |
| C | 5.3 | 3.7 | 5.7 | 9.6 | 2000 rps まで悪化なし |
| D | 4.5 | 5.6 | 4.3 | 5.5 | 2000 rps まで悪化なし |

p50 はどのパターンも 0.8〜1.1 ms でした。

### HTTP レイテンシ（p99 ms、タスクへ直接）

| パターン | 500 rps | 1000 rps |
|----------|---------|----------|
| A | 0.71 | 0.79 |
| B1 | 0.52 | 0.57 |
| B2 | 0.53 | 0.55 |
| C | 0.52 | 0.54 |
| D | 0.49 | 0.51 |

読み方：

- 直接接続では **host（D）が最も低く、Fargate（A）が最も高い** という仮説どおりの順番ですが、差は 0.3 ms 以内です。ALB を挟むと p99 が 5 ms 前後になり、この差は埋もれます
- 2000 rps までで頭打ちになったパターンはありませんでした。限界を比べるにはもっと高いレートか、重いペイロードが必要です
- B2 と C の直接接続は、障害シナリオ中にタスクが入れ替わって接続先が古くなったため、一度全件エラーになり、後から取り直しています

### 気づき

- **ENI・ポート・SG といった設定起因の障害（F-1〜F-3）は、どのモードでも 2 分以内に根本原因まで特定できた**。決め手は ECS イベントと CloudTrail で、モードの差はほとんど出なかった
- 粒度の差は出た。awsvpc（F-1 A）は「どのタスクの IP が unhealthy か」まで示し、bridge / host は「どのインスタンスか」まで
- **共有 SG の影響範囲の広がり（F-1 A → B1 / B2）は、本体の調査では「可能性」止まり** だった。タスク単位の SG を使えても、複数サービスで共有すると影響範囲の説明が難しくなる
- **host（F-5）では Container Insights のネットワークメトリクスがなく**、エージェントは EC2 の NetworkOut と ALB の ProcessedBytes で代用した。それでも帯域の上限超過は「仮説」止まりで、ENA の `bw_out_allowance_exceeded` などの OS レベルのデータが必要と自ら指摘した
- 調査の質を下げたのは監視の「穴」だった：F-2 はサーキットブレーカーが約 1 分でロールバックするためアラームが鳴らない、F-5 は ALB の `TargetResponseTime` の p99 が 78 ms にとどまり、クライアント側の p99 313 ms をアラームで捉えられない
- エージェントは CloudTrail から「同じ操作者が SG の削除 → 約 11 分後の復旧を繰り返している」ことを見抜き、意図的な障害注入の可能性を指摘した
- 誤りもあった：F-1 A で CloudTrail の結果が途中で切れて別の SG の削除と取り違えた（約 25 秒後に訂正）。F-5 では Flow Logs を「空」と判断したが、実際にはデータがあった（ロググループの `storedBytes` の更新遅れを見たとみられる）。F-1 D では最終欄に「No root causes identified」と表示されたが、本文では特定済みだった

| 使えるキャパシティ | Fargate / MI / EC2 | EC2 | MI / EC2 | 公式ドキュメント |

補足：

- 再デプロイの時間は 5 サービス同時の 1 回のみ。B2 と C は直前に 14 タスクから 2 タスクへ縮小した直後で、登録解除の待ちが残っていた可能性があります
- D（host）は `minimumHealthyPercent=100` にすると予備の台数がない限りデプロイできず、サーキットブレーカーで約 1 分後にロールバックされました（F-2）。普段は 50% にしているため、デプロイ中は処理能力が半分になります
- セキュリティプローブは B2 を対象にしていません（スクリプトが B1 のみ）。B2 も同じ awsvpc で、`ECS_AWSVPC_BLOCK_IMDS=true` が効く構成です
- 6.6（IPv6）と 6.9（GuardDuty）は今回扱っていません

## 仮説と結果

| 観点 | 仮説（ガイド 7.1） | 結果 |
|------|--------------------|------|
| 起動時間 | B1 は ENI の準備で遅く、多数を同時に起動すると上限で詰まる | **当たり**。B1 は 10 個中 2 個しか起動できない。ただし ENI の準備による遅さは B2 も同じで、約 9 秒 |
| スループット | ホスト間ではモードの差は小さく、インスタンスの帯域上限の影響が大きい | **ほぼ当たり**。1 接続は 1 フローの上限（5 Gbps）で全モード同じ。8 並列では A と C だけ半分程度に下がった（原因は未確定） |
| レイテンシ | host が最も低く、bridge はわずかに高い。ただし実際のアプリでは誤差の範囲 | **当たり**。直接接続で D が最小だが差は 0.3 ms 以内。ALB 経由では差が埋もれる |
| コスト | 小さいタスクを大量に動かすと、B1 と D は台数が増えて割高 | **当たり**。40 タスクで B1 は 3.3 倍、D は 6.7 倍 |
| モニタリング | awsvpc はタスク単位のデータがそろうので、DevOps Agent が影響範囲をタスク単位で特定しやすい | **一部当たり**。粒度は awsvpc だけタスク単位。ただし設定起因の障害の特定精度はモードによらず高かった |
| セキュリティ | host はコンテナからホストの資源に手が届き、分離が最も弱い | **当たり**。host だけが IMDS・ECS エージェント API・sshd に届く |

## 結論：選び方

```
Fargate を使う？ ─ Yes ─▶ awsvpc（選択肢なし）
  │No
  ▼
タスク単位の SG・Flow Logs・障害注入・Service Connect・localhost のサイドカーを使いたい？
  ─ Yes ─▶ awsvpc（EC2 なら必ずトランキングを有効化。無効だと小さいタスクで 3 倍以上のコスト）
  │No
  ▼
将来 Fargate / Managed Instances に移す可能性がある？ ─ Yes ─▶ awsvpc
  │No
  ▼
起動の速さ（数秒）と 1 台あたりのタスク数を最優先したい？ ─ Yes ─▶ bridge（動的ポート）
  │                                                    ※ Flow Logs はインスタンス単位、サイドカーは links が必要
  │No
  ▼
1 台 1 タスクで、ネットワーク性能を最優先し、ワークロードを信頼できる？
  ─ Yes ─▶ host（IMDS・ホスト資源に届く。デプロイには予備の台数か処理能力の一時低下が必要）
  │No
  ▼
awsvpc
```

叩き台からの変更点：

- awsvpc の分岐に「localhost のサイドカー」と「トランキング必須」を追加（6.5 とコストの結果から）
- bridge の判断軸を「同じポートのタスクを多数並べたい」から「起動の速さと密度」に変更（起動時間で最速だったため）
- host の条件に「1 台 1 タスク」と「デプロイの制約」を追加（F-2 の結果から）
- 性能（レイテンシ・スループット）はモード選びの決め手にならないことが分かったため、host の位置づけを下げた

## 付録 A. 検証中に見つかった問題と修正

リポジトリに次の修正を加えています（未コミット）。

| ファイル | 問題 | 修正 |
|----------|------|------|
| [docker/netbench/Dockerfile](../docker/netbench/Dockerfile) / [docker/loadgen/Dockerfile](../docker/loadgen/Dockerfile) | ベースイメージ由来の Critical / High の脆弱性（zlib、openssl、musl）が ECR スキャンで検出された | `apk upgrade --no-cache` を追加。再ビルド後は Critical / High が 0 件 |
| [docker/netbench/Dockerfile](../docker/netbench/Dockerfile) | 読み取り専用ルートで `/tmp` に空ボリュームをマウントすると root 所有になり、非 root（uid 101）の nginx が起動できない（`mkdir() "/tmp/client_temp" failed (13: Permission denied)`）。全サービスがサーキットブレーカーでロールバックした | `/tmp` を uid 101 所有にして `VOLUME ["/tmp"]` を宣言（ECS が権限を空ボリュームに引き継ぐ） |
| [cfn/03-services.yaml](../cfn/03-services.yaml) | iperf コンテナに書き込み先がなく、iperf3 が一時ファイルを作れない | iperf コンテナにも `/tmp` をマウント |
| [scripts/get-targets.sh](../scripts/get-targets.sh) | host モードでは `networkBindings` が空で、ポートが `null` と表示される | host モードではコンテナのポート（8080 / 5201）を使う |

ガイドに追記した方がよい点（未修正）：

- ECR の KMS 暗号化で、アカウントに AWS マネージドキー（aws/ecr）がまだない場合、初回の platform スタック作成が失敗することがある。スタックを削除して再実行すれば成功する
- `aws cloudformation deploy` は指定しなかったパラメータに **前回の値** を使う。`Desired*` を 0 で一度デプロイすると、次に省略しても 0 のまま
- EC2 のタスクでは `connectivityAt` が `createdAt` と同じになるため、`network_ready` は常に 0。ENI の準備時間は `pullStartedAt - createdAt` で見る必要がある
- `measure-startup.sh` は `run-task` の `failures` を表示しない（`--query` で捨てている）。失敗の理由は別途 `run-task` を実行して確認した
- F-2 は数十秒〜1 分でサーキットブレーカーがロールバックし、アラームが鳴らない。アラームを起点に調査を始める手順では捉えられない
- F-1 で負荷をかけていない場合、5xx は発生しない（ALB に届くリクエストがない）。プロンプトの症状は実際に起きているものに合わせる必要がある
- F-5 は ALB の `TargetResponseTime` が低いまま、クライアント側だけ遅くなることがある。p99 アラームでは捉えられない
- 障害シナリオでタスクが入れ替わると、直接接続の計測先（IP / ポート）が古くなる。直接接続の計測は障害シナリオの前に終えるか、直前に `get-targets.sh` を再実行する
